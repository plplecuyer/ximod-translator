# Brief — traduction des textes d'interface de XIMOD Translator

XIMOD Translator est un logiciel (Rust / egui) de traduction de mods pour les jeux Bethesda (Skyrim, Fallout 4, Starfield, Oblivion, Morrowind). Son interface est en Fluent (.ftl). Le fichier `source.json` contient 1163 clés : pour chacune, le texte anglais (`en`) et le texte français (`fr`, la référence d'origine — il fait foi quand l'anglais est ambigu).

Tâche : produire, pour chaque langue demandée, le fichier `<code>.json` (même dossier) — un objet JSON `{ "clé": "texte traduit", … }` avec TOUTES les clés de source.json, dans le même ordre. Écrire avec Python (json.dump, ensure_ascii=False, indent=1). Ne pas modifier source.json ni d'autres fichiers.

Règles impératives :
1. Les variables Fluent `{ $nom }`, `{ $count }`, `{ $n }`… sont copiées telles quelles (mêmes noms, mêmes accolades et espaces). Idem les littéraux `{" … "}` et les sélecteurs multi-lignes (`{ $more ->` / `[yes] …` / `*[no] …`) : garder exactement la structure, l'indentation de 4 espaces des lignes suivantes, ne traduire que le texte.
2. Ne pas traduire : les jetons `<a_A>`, `<n_A>`, `<br_A>`, les marqueurs `[[1]]`, les balises `<Alias=…>`, `<Global=…>`, les noms de produits et de formats (XIMOD, XIMOD Translator, XIMOD Architect, DeepL, Azure Translator, OpenAI, Google Cloud Translation, Fluent, Mod Organizer, Vortex, xTranslator, ESP-ESM Translator, Hunspell, SkyUI, MCM, DSD, SKSE, BSA, BA2, STRINGS, DLSTRINGS, ILSTRINGS, EET, SST, XML, JSON, CSV, INI, FOMOD, FormID, EDID, GRUP, QUST, DIAL, INFO, NPC, CTDA, NAM1, TRDT, esp, esm, esl, Creation Kit), les noms de jeux, les chemins (`assets/…`, `Config.ini`, `secrets.json`, `cache/online`), les codes (`{ $code }`), les signatures à quatre lettres, les noms de touches (Ctrl, Maj → l'usage local est admis : Shift/Strg/Ctrl selon la langue, mais les raccourcis Ctrl+G etc. restent lisibles), les symboles ✔ ✘ ✓ ✕ ⚠ · — › » ⇥.
3. Garder la ponctuation et les espaces de tête ou de fin du texte source ; garder les « … » (points de suspension), les deux-points finals (« Clé : » → forme locale), les parenthèses. Guillemets dans la langue cible (« » fr, „“ de/cs/pl, “” en, 「」 ja, 「」 ou “” zh, « » ru) mais jamais autour d'une variable.
4. Vocabulaire du domaine, à rendre de façon constante : « ligne » (une chaîne traduisible de la grille), « source » / « traduction », « plugin », « dictionnaire » (base de traduction .ximdb), « mod », « réplique » (ligne de dialogue INFO), « locuteur », « quête », « sujet » (topic DIAL), « statut » (Validé, En attente, À traduire, Traduit par similarité, Proposition modifiée, Personnalisé, Ignoré), « alias » (balise <Alias=…>), « fichier maître », « archive », « voix », « vue filtrée », « fenêtre d'édition ». Les noms des statuts doivent être traduits de la même façon dans toutes les clés où ils apparaissent.
5. Ton : interface professionnelle, concis, impératif pour les boutons et menus (« Ouvrir… », « Enregistrer »), forme polie pour les messages adressés à l'utilisateur. Longueur proche de l'original (ce sont des libellés de menus, boutons, colonnes, info-bulles, messages de barre d'état).
6. Norvégien : `nob` et `nor` reçoivent le même texte (bokmål). Chinois `zho` : simplifié. Portugais `por` : européen.
7. Ne rien inventer : si un terme n'a pas d'équivalent établi, garder le terme anglais ou français tel quel.

Vérification avant de finir : charger le JSON produit, vérifier qu'il a exactement les clés de source.json, et que pour chaque clé l'ensemble des `{ $… }` du texte traduit est identique à celui du texte anglais (même nombre, mêmes noms). Corriger puis réécrire tant que ce n'est pas le cas. Rendre compte en trois lignes : langues produites, nombre de clés, anomalies restantes (aucune attendue).
